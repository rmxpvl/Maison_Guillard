# S7 — Résumé : achat direct, nouvelle direction artistique et animations

> Travail du 20 au 23 octobre 2026 sur la branche `Branche-S7` (pas encore poussée au moment de
> l'écriture).
> Détail technique : `docs/specs/2026-10-20-s7-achat-direct-design.md` (design) et
> `docs/plans/2026-10-20-s7-achat-direct.md` (plan d'implémentation en 11 tâches).

## Contexte et organisation

- Deuxième des cinq blocs restants : site public (S6) → **achat direct** → demande de devis →
  back-office UI → back-office commandes et devis.
- Avant de commencer, les PR #4 (docs S6) et #5 (tests de l'API et documentation Swagger) ont été
  mergées dans `main`.
- Répartition du travail : j'ai tapé tout le code backend (modèles, migration, services, routes) ;
  les fichiers de test et le frontend ont été écrits pour moi puis expliqués.

## Décisions prises avec la cousine (stakeholder)

- **Pas de gestion de stock.** Un produit `disponible` se commande en quantité libre (de 1 à 10 par
  ligne). Quand il n'y en a plus, l'artisane le passe en `rupture` à la main. Le modèle de données
  reste celui de la doc technique (pas de colonne `stock`).
- **Paiement et livraison hors ligne.** La confirmation annonce : « Maison Guillard vous contacte
  sous 48 h pour le paiement et la livraison. » Adresse obligatoire, téléphone facultatif.
- **E-mail automatique à chaque commande, activable par l'artisane, désactivé par défaut.** Quand il
  est activé : un e-mail pour l'artisane (le détail de la commande) et un récapitulatif pour le
  client.
- **Nouvelle direction artistique** demandée en cours de bloc : plus de contraste, du noir « pour
  trancher », en prenant le site de Gilles & Boissier comme référence.

## Ce qui a été construit

### Backend

- **Trois tables** (une migration Alembic, appliquée aux bases de dev et de test, aller-retour
  `downgrade`/`upgrade` vérifié) : `commande`, `ligne_commande` et `parametre` (une seule ligne de
  réglages). Le `downgrade` supprime aussi le type PostgreSQL `statut_commande_enum`, qu'Alembic
  oublie.
- **`POST /api/commandes`** (public) :
  - validation Pydantic (e-mail valide, champs non vides même après suppression des espaces,
    au moins une ligne, quantité de 1 à 10, pas deux fois le même produit) → **422** sinon ;
  - le **prix est toujours lu en base**, jamais dans la requête, et copié dans
    `prix_unitaire_snapshot` : un client ne peut pas choisir son prix, et la commande garde le prix
    du jour si l'artisane le change ensuite ;
  - un produit en `rupture`, `sur_commande` ou inexistant → **422** avec un message qui le nomme ;
  - le total n'est pas stocké : il est recalculé à partir des lignes (`@property total`).
- **`GET` et `PUT /api/parametres`** (admin) : lire et changer `email_commande_actif`.
- **`email_service`** : prépare les deux e-mails, puis les envoie par SMTP (bibliothèque `smtplib`
  de Python) dans une **tâche de fond** FastAPI, après la réponse au client. Une erreur d'envoi est
  écrite dans les logs mais n'annule jamais la commande.
- **Supprimer un produit déjà commandé → 409** « passez-le en rupture » (au lieu d'une erreur 500) :
  une commande ne doit jamais perdre ses lignes.

### Frontend

- **Panier** : règles pures dans `utils/panier.js` (testées), état partagé par un Context React
  (`PanierProvider`, `usePanier()`), sauvegardé dans le `localStorage` du navigateur. Pastille du
  nombre d'articles dans l'entête, bouton « Ajouter au panier » actif pour les pièces disponibles.
- **Pages** `/panier` (quantités, retrait, total), `/commande` (formulaire + récapitulatif, bouton
  désactivé pendant l'envoi, messages d'erreur de l'API en français) et `/commande/confirmation`
  (numéro et montant, puis panier vidé).
- **Direction artistique noir et blanc** : fond blanc, texte et boutons noirs, gris neutre pour le
  texte secondaire (contraste 7,5:1), navigation en noir, **pied de page noir**. Presque tout tient
  dans les variables de couleur de `index.css`.
- **Animations** :
  - fondu enchaîné entre les photos d'une fiche produit (toutes les photos sont empilées, seule la
    sélectionnée est opaque) ;
  - glissement entre les pages : l'ancienne page part vers la gauche ou la droite selon la position
    de la nouvelle dans le menu, en s'effaçant, puis la nouvelle arrive en glissant
    (`TransitionPages.jsx`, avec `<Routes location>` pour garder l'ancienne page à l'écran pendant
    sa sortie) ;
  - les deux sont coupées si le visiteur a demandé à son système de réduire les animations.
- **Entête fixe** en haut de l'écran pendant le défilement (`position: sticky`).

## Tests

- Backend : **110 tests** pytest (80 au début du bloc). Le serveur SMTP est remplacé par un faux
  (`unittest.mock.patch`) : on vérifie qu'un e-mail part seulement quand le réglage est activé, et
  qu'une panne SMTP n'empêche pas la commande.
- Frontend : **19 tests** `node:test` (règles du panier, sens des transitions entre pages, règles
  d'affichage existantes).
- Tests manuels de l'API : `docs/tests-api.md`, sections 15 à 17 (16 vérifications, toutes PASS).
- Parcours complet dans le navigateur, avec réception réelle des deux e-mails dans Gmail.

## Erreurs rencontrées et ce qu'elles m'ont appris

1. **Les tests restaient bloqués sans rien afficher.** Docker Desktop était éteint, donc PostgreSQL
   aussi : pytest attendait une connexion qui ne venait jamais. **Réflexe : tests figés → vérifier
   que Docker tourne (`docker compose ps`).**
2. **Le catalogue ne s'affichait plus (erreur 502).** Le backend n'était pas lancé ; Vite servait la
   page mais son proxy ne trouvait personne sur le port 3000. Et `localhost:3000` affiché dans le
   navigateur donne un 404 normal : l'API n'a pas de page d'accueil. **Il faut deux terminaux :
   uvicorn (3000) et Vite (5173).**
3. **Les « View Transitions » ne faisaient rien.** L'attribut `viewTransition` de React Router ne
   fonctionne qu'en mode « Data » (`createBrowserRouter`), alors que le site utilise
   `<BrowserRouter>` : l'attribut était ignoré sans erreur. Trouvé en lisant la documentation livrée
   avec la bibliothèque. Remplacé par `TransitionPages`, qui marche dans notre mode. **Leçon :
   vérifier qu'une fonction s'applique à notre configuration avant de l'annoncer comme faite.**
4. **Connexion admin refusée dans Swagger (401).** Le mot de passe du `.env` ne correspondait plus
   à celui enregistré en base lors du seed de S4, et `seed.py` ne met pas à jour un admin existant.
   Le hash a été régénéré à partir du `.env`.
5. **Connexion SMTP refusée.** Le texte d'exemple `<les 16 lettres, sans espaces>` était resté tel
   quel dans `SMTP_PASSWORD`. Trouvé sans afficher le secret, en comparant sa longueur (30) à celle
   attendue (16).
6. **Les e-mails « n'arrivaient pas ».** Ils étaient bien envoyés, mais Gmail range dans « Messages
   envoyés » un e-mail dont l'expéditeur et le destinataire sont la même adresse. Ce ne sera plus le
   cas avec l'adresse de l'artisane.
7. **Mot de passe d'application Google** : le navigateur ouvrait le compte de l'école (connexion
   Microsoft) ; il faut passer par une fenêtre privée pour utiliser le compte Gmail personnel.

## À adapter au déploiement

Le site ne sera pas hébergé sur cet ordinateur. Avant la mise en ligne, seul le `.env` du serveur
change, pas le code :

- **Fournisseur SMTP** : Gmail personnel sert uniquement au développement ; utiliser le SMTP de
  l'hébergeur ou un service dédié (par exemple Brevo).
- **`EMAIL_ARTISAN`** : la vraie adresse de l'artisane (actuellement la mienne).
- **`EMAIL_EXPEDITEUR`** : de préférence une adresse au nom de Maison Guillard.
- **Interrupteur e-mail** : il passera dans l'interface admin avec le bloc back-office ; d'ici là,
  il se change dans Swagger (`PUT /api/parametres`).

## Ce qui a été construit

Trois nouveaux domaines métier, suivant le même pattern en couches déjà utilisé pour l'authentification
en S4 : **router** (reçoit la requête HTTP) → **schema Pydantic** (valide les données) → **service**
(logique métier, testable sans base de données réelle) → **modèle SQLAlchemy** (structure de la table).

### Catégories (`/api/categories`)

- Modèle `Categorie` (id, nom, slug unique).
- `GET /api/categories` — liste publique (pas besoin d'être connecté).
- `POST /api/categories` — admin seulement.
- `DELETE /api/categories/:id` — admin seulement. Refuse (`409 Conflict`) si un produit utilise encore
  cette catégorie — règle métier décidée pour éviter de casser l'intégrité du catalogue.

### Produits (`/api/produits`)

- Modèle `Produit` (nom, description, catégorie liée, prix, dimensions, disponibilité, date de création).
- `disponibilite` est un type énuméré fermé : `disponible`, `rupture`, `sur_commande` — impossible
  d'enregistrer une valeur invalide en base.
- `GET /api/produits` — liste publique, filtrable par `?categorie=` et `?disponibilite=`.
- `GET /api/produits/:id` — détail public.
- `POST` / `PUT` / `DELETE` — admin seulement. Le `PUT` accepte une **mise à jour partielle** :
  envoyer seulement `{"disponibilite": "rupture"}` ne touche pas les autres champs.

### Photos (`/api/produits/:id/photos`, `/api/photos/:id`)

- Modèle `Photo` (produit lié, URL, ordre d'affichage, indicateur "principale").
- `POST /api/produits/:id/photos` — upload d'un fichier (admin seulement).
- `PATCH /api/photos/:id/principale` — désigne une photo comme photo principale du produit ;
  désactive automatiquement l'ancienne principale (une seule à la fois, jamais deux en même temps).
- `DELETE /api/photos/:id` — suppression (admin seulement).
- Suppression en cascade : supprimer un produit supprime automatiquement ses photos.

**Décision importante** : l'intégration Cloudinary (service externe d'hébergement d'images prévu au
cadrage initial) est **stubbée** pour cette itération — pas de compte Cloudinary disponible pour
l'instant. À la place, les fichiers uploadés sont sauvegardés localement dans `backend/uploads/`
(dossier ignoré par Git) et servis directement par le serveur FastAPI via `/uploads/<fichier>`. La
fonction responsable (`upload_to_cloudinary`) garde exactement la même signature qu'aurait une vraie
intégration Cloudinary — la remplacer plus tard ne demandera de toucher qu'à cette seule fonction,
rien d'autre dans le reste du code.

## Tests

47 tests passent au total (14 hérités de S4 + 33 nouveaux) :

- **Tests unitaires** (services, base de données simulée) — vérifient la logique métier isolément :
  refus de suppression d'une catégorie utilisée, mise à jour partielle d'un produit, invariant
  "une seule photo principale par produit".
- **Tests d'intégration** (vraie base Postgres de test, client HTTP simulé) — vérifient le
  fonctionnement de bout en bout : authentification requise sur les routes admin, codes de statut HTTP
  corrects (200/201/204/401/404/409/422), upload de fichier réel suivi d'une relecture du fichier
  servi.

## Deux bugs rencontrés (hors plan initial, corrigés en cours de route)

1. Un fichier de test d'intégration oublié de charger les variables d'environnement (`load_dotenv()`)
   quand il est lancé seul, indépendamment des autres fichiers de test.
2. La dépendance `python-multipart`, nécessaire pour que FastAPI accepte les uploads de fichiers
   (`File`/`Form`), manquait de `requirements.txt` — ajoutée après coup.
